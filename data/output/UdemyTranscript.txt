Here is what you will build by the end of this course.

A small, working vehicle management application for Stark Group.

The scope is intentionally focused.

An authorized user will log in, register a new vehicle, view the vehicles already in

the system, update a record when something changes, and delete a vehicle when it is no longer needed.

And just like the build itself, these testing steps will be fully guided.

After the application works and the tests pass, you will take it through the final delivery steps.

You will push the project to GitHub, follow a simple CICD workflow, deploy the Flutter

Your goal is not just to watch someone build an application.

Before testing the complete VMS, we start small.

A unit test checks one focused piece of application behavior in isolation.

For our VMS, we will use the duplicate vehicle number rule.

We want to prove that an existing vehicle number is rejected while a new vehicle number is accepted.

A unit test should not depend on the real SQL database.

This lets us test only the vehicle service and its business rule.

The test becomes faster, repeatable and much easier to understand when something fails.

This is the first level of testing in our course.

Unit testing checks one rule.

Next, we will test the connected CRUD APIs

and after that the complete user journey from Flutter to Spring Boot and SQL.

For now, our goal is simple.

Prove one business rule before relying on the full application.

Our VMS is now connected, but a working screen is not enough to prove that the system is reliable.

Before deployment, we need to test it at different levels.

We will start small with one business rule, then test the connected backend through its APIs,

and finally test the complete application from the user's point of view.

Each test answers a different question and helps us find problems before the VMS goes live.

We begin with the duplicate vehicle number rule. This is a focused unit test,

because we are testing one piece of business behavior instead of running the whole application.

The repository is mocked, so we do not need the real SQL database.

We test two simple cases. An existing vehicle number should be rejected,

while a new vehicle number should be accepted.

If this test fails, we know the problem is inside this specific business rule.

To understand why the test matters, temporarily break the duplicate rule and run the test again.

This time, the test should fail. That failure proves that our test is

actually protecting the behavior we care about. We can then give anti-gravity the exact failure,

ask it to identify the cause, and apply the smallest correction.

Restore the proper rule, rerun the test, and confirm that it passes again.

Next, we move from one isolated rule to the connected backend.

Start Spring Boot and the SQL database. Then, run the complete CRUD scenario.

Create a vehicle, retrieve it, update it, verify the changed value, delete it,

and confirm that it is gone. We also test error cases such as duplicate vehicle numbers,

missing required fields, and invalid IDs. Unlike the unit test, this check proves

that the backend layers and the real database work correctly together.

Finally, we perform an end-to-end test. This time, we use the application exactly

as a real user would. Start the full local stack,

log in through Flutter, register a vehicle, confirm it appears in the list,

update a field, and then delete the record. We also try an error path by submitting a duplicate

vehicle number or incomplete data. The important point is that the entire journey

now travels through Flutter, the REST API, Spring Boot, and SWILL.

No mock vehicle data should be involved. By the end of this section, we have three

different levels of confidence. The unit test tells us whether one important business rule

behaves correctly. The API test tells us whether the backend components and SQL database work

together. And the end-to-end test tells us whether a real user can complete the full VMS journey

through the actual interface. If any step fails, we identify the failing layer,

make the smallest safe fix, and rerun the test.

Once these checks pass, the VMS is ready for the next stage, deployment.

26. What Is CI/CD?


======================================================================
Lecture 26: Course: Build a Full-Stack Web App with Flutter & Spring Boot
======================================================================

We have built and tested our VMS locally, now it is time to make it available online.

This is where CI-CD comes in. CI-CD gives us a structured way to move our application

from development to a live environment. CI stands for Continuous Integration.

In our project, this means reviewing our latest changes, committing them properly,

and pushing them to GitHub. This gives us a reliable and trackable version of both our

frontend and backend before deployment. CD stands for Continuous Deployment.

Once our code is available in GitHub, deployment platforms can build and publish the application.

Instead of keeping our VMS only on our computer, we make it accessible through a live URL.

Our VMS has two separate projects. The Flutter web frontend will be deployed through Netlify,

while the Java Spring Boot backend will be deployed through Render.

They remain separate projects, but once connected, they work together as one live VMS.

Before deploying anything, we need a clean and safe working state. The frontend and backend

must remain separate, and we should review our changes before pushing them. Passwords,

database credentials, API keys, and other secrets should never be committed to GitHub.

That is our goal for this section. We will first push both projects to GitHub. Then,

we will deploy the Flutter frontend to Netlify and the Spring Boot backend to Render.

Finally, we will connect both sides and test the complete VMS as a real live application.
